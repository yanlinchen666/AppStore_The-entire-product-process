## 四、故障处理策略

### 4.1 LLM API 调用失败

**降级策略**：每个 LLM 调用点都有 try/except，失败时降级到规则方案。

| 阶段 | 降级方案 | 代码位置 |
|------|---------|---------|
| 主题提取 | 预定义关键词匹配 + 词频统计 | [analysis_service.py:107-136](file:///D:/AI/agent_vc/AppStore_vc/AppStore_vc/backend/app/services/analysis_service.py#L107-L136) |
| PRD 生成 | 基于 finding 文本的模板化需求生成 | [prd_service.py:99-118](file:///D:/AI/agent_vc/AppStore_vc/AppStore_vc/backend/app/services/prd_service.py#L99-L118) |
| 测试用例生成 | 基于需求的通用测试模板 | [testcase_service.py:103-119](file:///D:/AI/agent_vc/AppStore_vc/AppStore_vc/backend/app/services/testcase_service.py#L103-L119) |

### 4.2 JSON 解析失败

- 所有 LLM 响应通过 `_parse_*_response` 方法解析
- 使用 `[` / `]` 边界提取，忽略非 JSON 前后缀
- 解析失败返回空数组，不抛出异常，不中断管道

### 4.3 向量索引 / 嵌入失败

- 单条评论 embedding 失败 → 跳过该条，不影响整体
- 整体索引构建失败 → 记录错误日志，后续证据检索降级为词重叠匹配
- 代码位置：[evidence_service.py](file:///D:/AI/agent_vc/AppStore_vc/AppStore_vc/backend/app/services/evidence_service.py)

### 4.4 数据库连接失败

- **连接池防护**：`pool_pre_ping=True` + `pool_recycle=60`，避免借出 stale 连接
- **Session 生命周期**：长耗时操作（LLM、HTTP）期间不持有 DB session
- **错误处理**：数据库异常被捕获后记录到 `AnalysisRun.error_message`，run 状态标记为 `failed`

### 4.5 异步管道阶段失败

- 管道分 9 个阶段，每个阶段独立 try/except
- 失败阶段发出 `failed` 进度事件
- **致命阶段**（采集、清洗、主题提取、问题发现、证据验证）失败 → 整个 run 标记为 `failed`
- **非致命阶段**（PRD 生成、测试用例生成）失败 → 记录错误，继续后续阶段，前面的结果仍然可见
- 代码位置：[analysis_orchestrator.py](file:///D:/AI/agent_vc/AppStore_vc/AppStore_vc/backend/app/services/analysis_orchestrator.py)

### 4.6 后端重启 / 进程中断

**问题**：后端在分析过程中重启（如 uvicorn `--reload` 触发），后台 pipeline 线程被杀死，但数据库里 run 仍显示 `running`，内存中进度事件丢失，前端看到进度永远 0%。

**恢复机制**：
- FastAPI `lifespan` 启动钩子自动扫描所有 `status="running"` 的旧 run
- 将其标记为 `failed`，error_message 写明「后端重启导致分析中断」
- 代码位置：[main.py lifespan](file:///D:/AI/agent_vc/AppStore_vc/AppStore_vc/backend/app/main.py)

**手动清理工具**：
- `python -m app.cleanup_zombies` （dry-run，仅检查）
- `python -m app.cleanup_zombies --apply` （实际删除僵尸 run）
- 代码位置：[cleanup_zombies.py](file:///D:/AI/agent_vc/AppStore_vc/AppStore_vc/backend/app/cleanup_zombies.py)

### 4.7 数据采集失败

- Apple RSS API 请求失败 → 重试一次，仍失败则抛出
- 空结果 → 不视为错误，提示"无新评论"
- 已采集过的评论 → 基于内容 hash 去重，不重复保存

## 五、减少幻觉与无依结论的措施

### 5.1 强制证据关联（核心机制）

**每条问题发现（finding）必须经过证据验证**：

1. LLM 生成 finding 后，不直接存库
2. 用 finding 的 `finding_text` 在 ChromaDB 中做向量检索
3. 计算每条相关评论的语义相似度（BGE-M3 embedding + 余弦相似度）
4. 相似度 > 0.5 的评论计为支撑证据
5. `evidence_review_ids` 字段记录所有支撑评论的 ID
6. 代码位置：[evidence_service.py:77-149](file:///D:/AI/agent_vc/AppStore_vc/AppStore_vc/backend/app/services/evidence_service.py#L77-L149)

### 5.2 无根据结论标记为假设

**判定规则**（任一条件即标记为假设）：
- `support_count == 0`（无任何证据支持）→ `is_assumption = True`
- `support_count < 2`（证据不足 2 条）→ `is_assumption = True`
- `confidence < 0.4`（置信度过低）→ `is_assumption = True`
- 其他情况 → `is_assumption = False`, `validation_status = "validated"`

**前端展示**：
- 已验证的 finding → 绿色"已验证"标签
- 假设的 finding → 黄色"假设"标签
- 代码位置：[RunDetail.tsx](file:///D:/AI/agent_vc/AppStore_vc/AppStore_vc/frontend/src/pages/RunDetail.tsx)

### 5.3 冲突检测

- 同时检索**支持证据**和**冲突证据**
- 冲突判定：语义相关 + （rating >= 4 或 sentiment > 0.1）的评论视为冲突反馈
- `has_conflict` 字段标记冲突存在
- `conflict_count` 统计冲突评论数
- 前端以红色"存在冲突"标签展示

### 5.4 置信度透明化

- 每条 finding 都带 `confidence` 值（0.0-1.0）
- 置信度计算公式：`support_count / (support_count + conflict_count)`
- 置信度在前端显式展示（百分比形式）
- 用户可以直观看到每条结论的可靠程度

### 5.5 模型生成与确定性统计严格区分

| 类型 | 标识方式 | 示例 |
|------|---------|------|
| 模型生成内容 | `is_model_generated = True` 字段 | `finding_text`、`requirement_text`、`case_title` |
| 确定性统计 | 单独字段存储，不与 LLM 输出混淆 | `sample_count`、`support_count`、`conflict_count`、`confidence`（计算值）、`sentiment`（词频统计） |

- 评论去重：确定性规则（内容 hash）
- 语言检测：`langdetect` 库（成熟统计模型，非 LLM）
- 情感分析：词频统计（粗粒度，无幻觉风险）
- 追溯链：数据库外键关联，确定性验证

### 5.6 完整追溯链

```
Review（真实评论）
   ↓ evidence_review_ids
Finding（问题发现）
   ↓ finding_id + source_review_ids
Requirement（PRD 需求）
   ↓ requirement_id
TestCase（测试用例）
```

每一层都可以向上追溯到原始评论，任何结论都能找到真实数据支撑。

### 5.7 Prompt 约束

所有 LLM 调用的 Prompt 都包含：
- **明确的输出格式**（JSON 结构）
- **强制关联原始数据**（`source_review_ids`、`source_findings`、`requirement_id`）
- **数量约束**（5-10 条需求、2-4 个测试用例）
- **角色设定**（product analyst / product manager / QA engineer）

### 5.8 真实数据原则

- **数据库只存真实 App Store 评论数据**，不使用任何模拟/生成数据
- 采集来源是 Apple 官方 RSS Feed API
- 所有分析结论基于真实用户评论生成
- 符合项目约束："Only use real data, no simulated data"

## 六、补充：各阶段实现方式选型说明

| 阶段 | 实现方式 | 选型理由 |
|------|----------|---------|
| 数据采集 | 确定性规则（HTTP + JSON 解析） | RSS API 返回结构化数据，无需 LLM |
| 评论去重 | 确定性规则（内容 hash） | 精确匹配，无歧义 |
| 字段规范化 | 确定性规则（正则、strip） | 格式问题，规则更可靠 |
| 语言检测 | 确定性库（langdetect） | 成熟统计模型，零幻觉 |
| 情感分析 | 确定性词频统计 | 粗粒度过滤，不需要细粒度情感 |
| 主题发现 | LLM（Qwen3-8B） | 语义聚类，需泛化能力，硬编码关键词无法覆盖 |
| 问题发现 | LLM（Qwen3-8B） | 需理解上下文与抽象问题，规则无法覆盖 |
| 证据检索 | 向量相似度（BGE-M3） | 语义匹配，优于关键词匹配 |
| 冲突检测 | 规则 + 向量 | rating + sentiment + 语义相关度组合判断 |
| PRD 生成 | LLM（Qwen3-8B） | 需求写作是创造性任务 |
| 测试用例生成 | LLM（Qwen3-8B） | 测试场景设计需要推理 |
| 追溯链 | 确定性规则（数据库外键） | 数据完整性约束，必须可验证 |
